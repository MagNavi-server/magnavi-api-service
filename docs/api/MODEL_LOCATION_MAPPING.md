# 모델 코드 → 장소 내부 조회 — 4-2단계

구현일: 2026-09-22

이 기능은 모델의 출력 코드에 연결된 건물·층·장소를 찾는다. 같은 Spring 프로그램 안에서 Java 메서드로 호출하며, HTTP 경로·gRPC 통신·Python 호출은 추가하지 않았다.

[장소 조회 API](PLACE_API.md) · [place 모듈](../modules/PLACE.md) · [DB 스키마](../../DATABASE_SCHEMA.md)

## 1. 호출 방법

호출할 클래스는 `place.application.ModelLocationQueryService`다. 다른 모듈에서는 이 서비스를 주입받고 다음 메서드를 사용한다.

```java
// 세 값은 설명용 예시다. 대응하는 매핑이 DB에 등록되어 있어야 성공한다.
IndoorLocationInfo location = modelLocationQueryService.findLocation("building-a", "v1", "7");
```

| 입력 | 의미 | 허용 범위 |
|---|---|---|
| `modelKey` | 모델 종류·적용 구역을 구분하는 이름 | 필수, 최대 128자 |
| `modelVersion` | 사용한 모델의 버전 식별자 | 필수, 최대 64자 |
| `locationCode` | 모델이 반환하는 위치 코드 | 필수, 최대 50자 |

null·빈 문자열·공백만 있는 값은 거절한다. 길이는 Java의 UTF-16 길이가 아닌 유니코드 코드 포인트 수로 검사해 기존 엔티티·MySQL 컬럼의 정책에 맞춘다.

세 값 모두 기존 저장 정책과 동일하게 **대소문자·앞뒤 공백·앞자리 0을 그대로 보존**한다. `v1`과 `V1`, `7`과 `007`, `7`과 `7 `은 서로 다른 값이다. 위치 코드를 숫자나 장소 ID로 변환하지 않는다. 실제 모델이 사용할 식별자 규칙은 이후 통신 계약과 기준 데이터 등록 시 맞춘다.

## 2. 처리 흐름

```text
ModelLocationQueryService.findLocation(모델 키, 버전, 코드)
  → 필수 값·길이 검사
  → ModelLocationPersistenceAdapter의 읽기 전용 트랜잭션
  → 세 값이 모두 같은 model_location_mappings 행 조회
  → 등록된 indoor_location_id로 활성 장소·층·건물 JOIN 조회
  → IndoorLocationInfo 반환
```

기존 `ModelLocationMappingJpaRepository`와 `PlaceReadRepository`를 재사용한다. 성공할 때 매핑 조회 1회와 장소 조회 1회로 처리하며, 장소마다 건물·층을 따로 읽지 않는다. 매핑이 없으면 첫 조회에서 끝난다.

결과인 `IndoorLocationInfo`에는 내부 장소 ID, 건물 ID·이름·주소, 층 ID·실제 층 번호·이름, 장소 이름·설명이 들어간다. 예측 점수·회원 정보·위치 이력은 포함하지 않는다. 반환값은 DB 엔티티가 아니라 필요한 값만 담은 DTO이므로 다른 모듈이 내부 저장 객체를 직접 수정하지 않는다.

## 3. 실패 처리

| 상황 | 서비스가 전달하는 오류 |
|---|---|
| 입력 누락·공백만 입력·길이 초과 | `PlaceException`, `Reason.INVALID_INPUT`, 잘못된 필드 이름 |
| 모델 키·버전·코드가 일치하는 매핑 없음 | `PlaceException`, `Reason.NOT_FOUND` |
| 매핑이 가리키는 장소가 비활성 상태이거나 조회 불가 | `PlaceException`, `Reason.NOT_FOUND` |

매핑 누락과 비활성 장소는 모두 **사용 가능한 연결 대상 없음**으로 취급한다. 오류에 입력 원문이나 SQL을 담지 않는다. 이 기능은 내부 메서드이므로 자체 HTTP 상태 코드나 gRPC 상태 코드는 없다. 이후 통신 계층이 오류를 어떻게 전달할지는 연동 단계에서 정한다. DB 접속 장애 등 기술 오류를 대상 없음으로 숨기지 않는다.

다른 버전의 매핑, 기본 장소, 모델 코드와 같은 숫자의 장소 ID로 대체하지 않는다. 비활성 장소와 기존 매핑 행은 삭제하지 않는다.

## 4. 모델 버전과 실제 데이터

모델 버전은 학습 결과·모델 묶음을 구분하는 이름이다. 위치 코드가 늘어났을 때뿐 아니라 같은 코드를 유지하며 정확도를 개선했을 때도 새 버전을 사용할 수 있다. 모델 버전과 Flyway의 DB 스키마 버전은 별개다.

새 모델 버전을 사용하려면 그 버전의 매핑 행을 먼저 준비한다. 코드의 의미가 같다면 기존 장소에 연결하고, 새 장소라면 장소를 등록한 다음 연결한다. 보통 테이블 구조나 조회 코드를 변경할 필요는 없다. 이전 버전의 행을 보존하면 이전 모델로 돌아갈 때 사용할 수 있다.

이번 구현은 **조회 기능과 테스트용 합성 데이터 검증**까지다. 실제 모델 키·버전·코드와 장소의 대응표를 자동 생성하거나 실서비스 DB에 등록하지 않았다. 적용 구역과 장소의 소속 건물 일치는 검증된 자료로 등록할 때 확인해야 하며, 현재 모델 키 문자열 자체에서 건물을 알아내지는 않는다.

## 5. 검증과 다음 연결

`ModelLocationQueryIntegrationTests`는 격리된 MySQL에서 14개 테스트를 실행한다. 모델·버전·대소문자·공백·앞자리 0 구분, 비숫자 코드, 입력 제한, 유니코드 최대 길이, 누락·비활성 처리, 여러 코드의 같은 장소 연결, 활성 상태 변경 반영, SQL 횟수와 쓰기 없음 등을 확인한다. 합성 자료는 테스트 종료 시 롤백한다.

```bash
./gradlew test --tests '*ModelLocationQueryIntegrationTests'
./gradlew build
```

실제 Python과의 통신은 검증하지 않았다. 이후 gRPC 단계에서 `positioning`이 선택한 모델 범위와 수신한 버전을 확인한 뒤 이 서비스를 호출하도록 연결한다. Python의 현재 정수 예측값을 문자열 코드로 바꾸는 규칙과 준비 중·오류 상태 처리는 그때 합의한다.

현재는 자체 캐시 없이 호출마다 DB를 조회한다. 센서 샘플마다 호출하도록 연결한 상태가 아니며, 실시간 연동 시 호출 빈도·지연을 검증하고 필요하면 모델 버전·장소 활성 상태·매핑 변경을 고려한 캐시 정책을 마련한다.
