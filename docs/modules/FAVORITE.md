# favorite — 즐겨찾기 모듈

작성일: 2026-09-10 · 상태: 구현 예정 설계

[전체 모듈 안내](README.md) · [장소 모듈](PLACE.md) · [Spring 구현 계획](../../IMPLEMENTATION_PLAN.md) · [DB 스키마](../../DATABASE_SCHEMA.md)

## 1. 무엇을 하는 모듈인가?

favorite는 “사용자가 나중에 다시 보고 싶은 대상을 저장하는 기능”을 담당한다.

예를 들어 A 사용자는 A관 205호 앞을 저장하고, B 사용자는 같은 205호 앞과 버스 정류장을 저장할 수 있다. 저장된 대상이 같아도 각자의 즐겨찾기는 별개다.

내부 장소 기준 정보와 네이버 외부 검색 연동은 place가 맡는다. 외부 검색 결과는 우리 DB의 장소 행이 아닐 수 있다. favorite는 누가 무엇을 저장했는지와 그 저장 항목을 관리한다.

## 2. 구현할 기능

| 기능 | 기존 API를 기준으로 한 경로 |
|---|---|
| 즐겨찾기 등록 | `POST /favorites/` |
| 내 즐겨찾기 목록 | `GET /favorites/` |
| 내 즐겨찾기 삭제 | `DELETE /favorites/{favorite_id}` |

모든 기능은 MagNavi 토큰으로 인증한 본인을 기준으로 동작한다. 일반·카카오·구글 로그인 여부가 아니라 내부 member_id가 소유권 기준이다. 명시적으로 연결된 로그인 수단은 같은 회원의 목록을 사용한다.

기존 유형은 장소 `place`, 버스 `bus`, 정류장 `busStop`이다. 새 구조에서도 버스와 정류장 기능을 빠뜨리지 않는다. 수정·폴더·공유 즐겨찾기는 현재 기본 이관 범위에 포함하지 않는다.

## 3. 즐겨찾기 ID와 대상 ID를 구분하자

이 구분이 이 모듈에서 가장 중요한 부분이다.

| 즐겨찾기 자체 ID | 회원 ID | 저장한 대상 |
|---|---|---|
| 501 | A 회원 | 205호 앞 장소 |
| 502 | B 회원 | 205호 앞 장소 |
| 503 | B 회원 | 특정 정류장 |

501과 502는 다른 즐겨찾기이지만 같은 장소를 가리킨다. A가 501을 삭제해도 B의 502나 205호 앞 장소 정보는 없어지지 않는다.

현재 원본 테이블은 앱이 보낸 즐겨찾기 `id`를 전체 회원에 걸쳐 유일한 PK로 사용한다. 앱이 대상 장소 ID를 여기에 넣으면 서로 다른 회원이 같은 대상을 저장할 때 충돌할 수 있다.

목표는 즐겨찾기 자체 ID를 별도로 두고, 같은 회원이 같은 대상을 중복 저장하는 것만 제한하는 것이다.

## 4. 어떤 정보를 저장하는가?

| 정보 | 의미 |
|---|---|
| id, member_id | 즐겨찾기 자체 ID와 소유 회원 FK |
| target_type, target_key | 대상 유형과 서버가 만든 중복 판별 키 |
| indoor_location_id | 내부 실내 장소를 가리킬 때만 사용하는 실제 FK |
| outdoor_place_id — 선택 | 자체 실외 장소 테이블을 도입할 때만 추가하는 FK |
| provider, external_id | 제공처와 실제 외부 ID, 있을 때만 사용 |
| 최소 표시 정보 — 조건부 | 저장이 허용된 이름·주소·좌표·교통 정보 등 |
| 생성·수정 시각, 선택적 legacy_id | 관리와 이전 앱 호환 |

대상 유형 초안은 INDOOR_PLACE·OUTDOOR_PLACE·EXTERNAL_PLACE·BUS·BUS_STOP이다. 기존 앱의 place·bus·busStop에서 어떻게 변환할지 합의한다.

기본 중복 제약은 member_id·target_type·target_key 조합이다. 내부 장소는 실제 FK로도 보호하고, 한 행이 서로 다른 유형을 동시에 가리키지 못하게 검증한다. 상세 컬럼·NULL 조합·제약은 [DB 스키마](../../DATABASE_SCHEMA.md)를 따른다.

### 4.1 네이버 검색 결과는 어떻게 구분하는가?

현재 지역 검색 응답에는 고유 장소 ID가 명시되어 있지 않다. 따라서 naver_place_id 필수 컬럼을 전제로 하지 않는다. [지역 검색 명세](https://api.ncloud-docs.com/docs/naver-api-hub-search-local)

즐겨찾기 자체 ID는 서버가 발급한다. 같은 실제 장소인지 비교하는 키는 별개다. 저장 허용 후 이름·주소·좌표를 이용한 키를 검토할 수 있지만, 이름 변경·이전·같은 건물의 여러 업체를 완벽히 구분한다고 보장하지 않는다. 해시값도 공식 장소 ID는 아니다.

네이버 결과의 캐시·영구 저장 가능 범위는 아직 미확정이다. 허용 필드·기간·표시·갱신·삭제 조건을 확인하기 전에는 외부 스냅샷 저장을 활성화하지 않는다. 검색 기능 자체와 저장 기능의 준비 상태를 구분한다.

### 4.2 버스·정류장

실제 제공처의 노선·정류장 식별자를 사용한다. 지역·방향 등 식별 범위를 맞추고 표시 이름이나 버스 번호만으로 같은 대상으로 판단하지 않는다. 기존 bus_number·station_name·station_id 필드는 호환 기준으로 확인한다.

## 5. 등록 흐름

예시: A 사용자가 앱에서 “205호 앞 즐겨찾기” 버튼을 누른다.

1. 보안 계층에서 인증한 A의 회원 ID를 얻는다.
2. Controller가 대상 유형과 필수 정보를 검사한다.
3. 내부 장소라면 place의 공개 조회 기능으로 존재를 확인한다.
4. favorite Service가 A에게 동일 대상이 이미 등록되어 있는지 확인한다.
5. 서버가 대상 키와 새 즐겨찾기 ID를 만들고 A와 대상을 연결해 저장한다.
6. DB의 회원·대상 중복 제약도 확인한다.
7. 생성된 즐겨찾기 ID와 표시 정보를 앱에 반환한다.

```text
A의 등록 요청
  → 인증한 A의 ID 확인
  → 대상 확인
  → A의 중복 여부 확인
  → 즐겨찾기 501 저장
  → 등록 결과 반환
```

B가 같은 장소를 등록하면 별도의 즐겨찾기 502를 생성할 수 있다.

외부 장소는 저장 허용과 선택 정보 검증을 먼저 거친다. place가 정의한 검색 결과 계약을 사용하고, 서버가 발급한 선택 참조 등으로 전달값을 확인할지 정한다. 실제 고유 ID가 없는 네이버 결과에 ID 상세 조회 API가 있다고 가정하지 않는다. 외부 통신은 긴 저장 트랜잭션 밖에서 처리한다.

## 6. 중복 요청은 어떻게 처리하는가?

앱의 버튼 연속 클릭이나 네트워크 재시도로 같은 요청이 두 번 올 수 있다.

사전 조회만으로는 두 요청이 동시에 “아직 없음”을 확인할 수 있다. 따라서 중복 금지는 DB 제약으로도 보장한다.

초기 제안은 같은 회원·대상의 중복 등록을 409 등 명확한 중복 응답으로 처리하는 것이다. 이미 등록된 항목을 그대로 반환하는 방식으로 바꾸려면 API 정책을 먼저 정한다.

등록 중 장소가 삭제되는 경우도 고려한다. 내부 장소 참조를 DB에서 보호할 수 있게 설계하면 “확인할 때는 있었지만 저장할 때는 없는 장소”를 연결하는 문제를 막을 수 있다.

## 7. 내 목록 조회 흐름

예시: B 사용자가 즐겨찾기 화면을 연다.

1. 인증된 회원 ID B를 얻는다.
2. 목록 범위와 최대 개수를 검사한다.
3. DB에서 `member_id=B`인 항목만 조회한다.
4. 필요한 경우 장소 표시 정보를 정해진 방식으로 조합한다.
5. B의 목록만 반환한다.

```text
B의 목록 요청 → B 소유 항목 조회 → 필요한 표시 정보 → B에게 반환
```

다른 사용자 ID를 요청에 넣어도 그 사용자의 목록을 조회하지 않는다.

내부 장소는 공개 조회로 최신 정보를 조합할 수 있다. 외부 장소는 저장 허용 범위에서만 등록 당시 표시 정보를 보관하는 방안을 검토한다. 전자는 스냅샷이라고 하며 “그 시점의 표시 정보를 복사해 둔 것”을 뜻한다.

최신 내부 정보를 합칠 경우 목록 항목 하나마다 DB를 반복 조회하지 않도록 묶음 조회 등을 검토한다. 외부 상세를 고유 ID로 다시 조회할 수 있다고 가정하거나 목록 전체에 외부 API 호출을 반복하지 않는다. 외부 대상이 사라졌을 때도 목록 전체가 실패하지 않게 표시 정책을 정한다.

## 8. 삭제 흐름

예시: A 사용자가 즐겨찾기 501을 삭제한다.

1. 인증한 회원 ID A와 즐겨찾기 ID 501을 받는다.
2. `id=501`이고 `member_id=A`인 항목을 조회한다.
3. 있으면 트랜잭션 안에서 그 항목만 삭제한다.
4. 없거나 본인 소유가 아니면 합의한 오류를 반환한다.
5. 장소 원본과 다른 회원의 즐겨찾기는 유지한다.

```text
A / 501 삭제 요청 → A 소유인지 확인 → 501만 삭제 → 완료 응답
```

타인의 항목과 없는 항목을 같은 404로 처리하는 방식은 기존 API와 맞출 수 있다. 다른 사람의 즐겨찾기 존재 여부를 별도로 알려줄 필요는 없다.

이미 삭제된 항목을 다시 삭제했을 때 오류를 반환할지 성공으로 볼지는 반복 요청 정책으로 정한다.

## 9. 내부 구조와 모듈 경계

| 계층 | 예시 구성요소 | 역할 |
|---|---|---|
| presentation | `FavoriteController`·DTO | 등록·조회·삭제 요청 변환 |
| application | `FavoriteService` | 소유권·대상 확인과 업무 흐름 |
| domain | `Favorite`, 대상 식별 정보, 저장소 인터페이스 | 중복·유형·소유권 규칙 |
| infrastructure | JPA 저장소·조회 구현 | 실제 데이터 저장·조회 |

favorite가 내부 place 정보를 필요로 하면 공개된 조회 기능을 호출한다. 네이버 연동은 place의 어댑터에 두고 favorite에는 제공자 원본 응답 대신 합의한 최소 DTO만 전달한다. place의 내부 Repository를 가져와 장소를 수정하지 않는다.

인증된 사용자 정보는 보안 계층에서 전달받는다. member의 비밀번호나 JWT 서명 키를 알 필요는 없다.

place가 favorite를 다시 직접 호출해야만 동작하는 순환 구조는 피한다. 참조 중 삭제 정책처럼 두 영역에 걸친 문제는 DB 무결성과 업무 조합 위치를 함께 정한다.

## 10. 트랜잭션과 오류 처리

등록·삭제는 짧은 업무 트랜잭션으로 관리한다. 외부 교통 API처럼 오래 걸릴 수 있는 통신을 DB 트랜잭션 전체와 무조건 묶지 않는다.

| 상황 | 처리 방향 |
|---|---|
| 인증되지 않음 | 인증 실패 |
| 유형별 필수 정보 누락 | 입력 오류 |
| 존재하지 않는 내부 장소 | 대상 없음 |
| 같은 회원의 중복 대상 | 중복 오류 또는 합의한 반복 등록 결과 |
| 다른 회원의 항목 삭제 | 거절, 기존 API 기준 404 검토 |
| 대상 정보가 이후 변경·삭제됨 | 확정한 참조·표시 정책 적용 |
| 외부 저장 미허용·미확정 | 해당 저장을 거절·보류, 검색 결과를 무단 축적하지 않음 |

## 11. 구현 전에 결정할 사항

- 기존 앱 ID와 새 자체 ID의 연결 및 응답 호환.
- 내부 실내·선택 실외·외부 장소의 유형 구분.
- 네이버 스냅샷의 저장·보관·표시 허용 조건.
- 고유 장소 ID가 없는 결과의 중복 판단과 갱신 한계.
- 교통 제공처·지역·노선·정류장 식별 범위.
- 반복 등록·삭제 응답과 내부 장소 삭제·비활성화 정책.
- 로그인 수단 연결 전후 동일 회원의 목록 처리.

## 12. 완료 확인

- [ ] A와 B가 같은 장소를 각각 저장할 수 있다.
- [ ] 같은 회원의 중복 등록을 동시 요청에서도 처리한다.
- [ ] 내 목록에 다른 회원 항목이 포함되지 않는다.
- [ ] 타인의 즐겨찾기를 삭제할 수 없다.
- [ ] 즐겨찾기 삭제가 장소 원본 삭제로 이어지지 않는다.
- [ ] 장소·버스·정류장 유형을 모두 검증한다.
- [ ] 기존 ID·목록·삭제 API 호환을 확인한다.
- [ ] 소셜 제공자가 달라도 연결된 같은 member_id의 목록을 사용한다.
- [ ] 네이버 공식 장소 ID를 가정하지 않고 외부 저장 조건을 검증한다.
- [ ] 참조 대상 변경과 반복 요청 정책을 테스트한다.
