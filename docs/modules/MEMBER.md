# member — 회원과 인증 모듈

최초 작성일: 2026-09-10 · DB 기반 반영일: 2026-09-20

현재 구현: Member·LocalCredential·SocialAccount의 JPA 매핑과 내부 저장소 3개를 구현했다. 로그인 ID는 앞뒤 공백 제거 후 대소문자를 구분하며 이메일·전화번호는 선택, 이메일 중복은 허용한다. 새 회원 객체의 권한·상태는 USER·ACTIVE다. 저장·조회·고유/FK·부분 저장 롤백을 실제 MySQL에서 검증했다. 아래 가입·로그인·JWT·소셜 검증 API 흐름과 기존 PersistenceAdapter는 후속 구현이다.

[전체 모듈 안내](README.md) · [Spring 구현 계획](../../IMPLEMENTATION_PLAN.md) · [DB 스키마](../../DATABASE_SCHEMA.md)

## 1. 무엇을 하는 모듈인가?

member는 “서비스 회원이 누구이며 어떤 방법으로 로그인하는가?”를 관리한다.

일반 ID·비밀번호 로그인과 카카오·구글 로그인을 지원하는 방향이다. 로그인 수단은 여러 개일 수 있지만 회원 본체는 별도로 관리한다. 소셜 계정을 명시적으로 연결하면 같은 회원의 정보와 즐겨찾기를 유지할 수 있다.

쉽게 말해 회원 명부와 여러 종류의 출입증을 관리하는 곳이다. 장소 검색·모델 추론은 다른 모듈의 일이다.

## 2. 구현할 기능

| 기능 | 기존 경로 또는 구분 | 설명 |
|---|---|---|
| 일반 회원가입 | POST /users/signup | 회원과 일반 로그인 정보를 함께 생성 |
| 일반 로그인 | POST /users/login | 비밀번호 확인 후 서비스 토큰 발급 |
| 내 정보 조회 | GET /users/me | 로그인 방법과 무관하게 본인 조회 |
| 이름 변경 | PUT /users/me/username | 본인의 표시 이름 변경 |
| 카카오·구글 로그인 | 신규, 경로 미정 | 제공자 인증 검증 후 회원 조회·생성 |
| 소셜 계정 연결 | 초기 포함 여부 결정 | 본인 확인 후 기존 회원에 로그인 수단 추가 |

기존 일반 로그인을 유지하는 안이다. API·필드 호환 범위는 앱과 합의한다. 경로가 적혀 있어도 Spring에 구현되어 있다는 뜻은 아니다.

로그아웃·재발급·탈퇴·비밀번호 변경·계정 연결 해제의 초기 포함 여부는 별도로 정한다. 계정 연결을 구현하지 않으면 제공자별로 따로 가입한 회원이 자동으로 같은 회원이 되지는 않는다.

## 3. 어떤 정보를 관리하는가?

| 테이블 | 관리 정보 |
|---|---|
| members | 내부 회원 ID·표시 이름·연락처·권한·상태 |
| local_credentials | 회원 ID·로그인 ID·비밀번호 해시 |
| social_accounts | 회원 ID·제공자·제공자의 사용자 ID |

예시: members의 101번 회원에 일반 로그인 한 개와 KAKAO 연결 한 개가 붙을 수 있다. 소셜 전용 회원에게는 local_credentials 행이 없어도 된다.

로그인 ID와 비밀번호는 members에 넣지 않는다. 비밀번호 원문·해시·서명 키를 응답에 포함하지 않는다.

members.email은 연락용이며 전역 UNIQUE를 두지 않는다. 이메일·전화번호는 선택값으로 확정했다. 소셜 이메일·전화번호를 항상 받을 수 있다고 가정하지 않는다. 기존 앱의 일반 가입 폼·응답도 API 전환 시 이 정책에 맞춘다.

컬럼·FK·고유 제약의 상세 기준은 [DB 스키마](../../DATABASE_SCHEMA.md)다.

## 4. 일반 회원가입은 어떻게 동작하는가?

1. Controller가 로그인 ID·이름·비밀번호 등 입력을 검사한다.
2. Service가 local_credentials의 로그인 ID 중복을 확인한다.
3. 비밀번호 해싱 도구가 검증용 해시를 만든다.
4. 짧은 트랜잭션에서 members와 local_credentials를 함께 저장한다.
5. DB 고유 제약으로 동시에 들어온 중복 가입도 차단한다.
6. 비밀번호 정보가 없는 응답을 반환한다.

두 번째 테이블 저장이 실패하면 첫 번째 회원 생성도 되돌린다. 회원만 생기고 로그인 정보가 없는 부분 저장을 막는 것이다.

해시는 나중에 복호화하는 암호화와 다르다. 로그인 때 전용 검증기로 입력한 비밀번호와 저장된 해시가 맞는지 비교한다. 계산이 필요한 해싱은 가능한 한 긴 DB 커넥션 점유와 분리한다.

## 5. 일반 로그인과 소셜 로그인 흐름

### 5.1 일반 로그인

1. local_credentials에서 로그인 ID를 찾는다.
2. 비밀번호 해시를 검증한다.
3. 연결된 members의 상태를 확인한다.
4. 내부 회원 ID를 기준으로 MagNavi 액세스 토큰을 발급한다.

기존 로그인은 username·password를 폼으로 받고 access_token·token_type을 반환한다. JSON 전환이나 필드 변경은 앱과 합의한다.

### 5.2 카카오·구글 로그인

1. 앱 SDK 또는 서버 인증 흐름에 맞는 인증 결과를 받는다.
2. 제공자 규격에 맞게 서명·발급자·대상 앱·만료 등을 검증한다.
3. 검증된 provider와 provider_user_id로 social_accounts를 조회한다.
4. 기존 연결이면 해당 회원을 사용한다. 없으면 회원과 소셜 연결을 함께 생성한다.
5. 회원 상태 확인 후 MagNavi 자체 액세스 토큰을 발급한다.

제공자 검증 통신을 긴 DB 트랜잭션으로 감싸지 않는다. 최초 로그인 두 건이 동시에 도착해도 소셜 계정 고유 제약으로 중복 회원을 방지하고, 실패한 회원 생성은 롤백한다.

구글은 sub, 카카오는 서비스 앱의 회원번호로 식별한다. 이메일을 계정 ID로 사용하지 않는다. 참고: [Google 식별자](https://developers.google.com/identity/openid-connect/openid-connect), [Kakao 로그인](https://developers.kakao.com/docs/ko/kakaologin/common).

앱이 보낸 사용자 ID나 이메일만 신뢰하지 않는다. 사용할 SDK·인가 코드 교환·ID 토큰 검증 방식을 제공자별로 정하고, 해당 방식에 필요한 state·nonce·PKCE·재사용 방어를 적용한다. 모든 제공자가 같은 형태의 토큰을 준다고 가정하지 않는다.

### 5.3 계정 연결

이메일이 같다는 이유만으로 자동 병합하지 않는다. 연결 기능을 제공한다면 기존 회원의 재인증과 새 소셜 계정 인증을 모두 거친다. 이미 다른 회원에게 연결된 소셜 계정은 가져오거나 덮어쓰지 않는다.

제공자 토큰·인가 코드는 로그인 이력처럼 기본 저장하지 않는다. 외부 API 지속 호출이 필요한 별도 기능이 생기면 보관 필요성과 보안 정책을 다시 설계한다.

## 6. 로그인 이후 요청은 어떻게 확인하는가?

예시: 앱이 `Authorization: Bearer <MagNavi 토큰>` 헤더와 함께 내 정보 조회를 요청한다. 일반·카카오·구글 로그인 모두 이후에는 같은 서비스 토큰 체계를 사용한다.

1. Spring Security가 토큰을 읽는다.
2. 서명과 만료 시각, 설정한 발급자·대상 등의 조건을 검증한다.
3. 유효하면 인증된 사용자 정보를 요청 처리 코드에 전달한다.
4. Controller와 Service는 이 식별자로 본인의 데이터를 처리한다.

```text
토큰이 있는 요청
  → 보안 계층의 검증
  → 인증된 사용자 식별자
  → 해당 사용자의 업무 처리
```

토큰 검증은 “이 사람이 누구인지”를 확인하는 인증이다. “다른 사람의 즐겨찾기를 삭제해도 되는가?”는 권한 문제이므로 해당 업무 모듈에서 추가로 검사한다.

Resource Server 의존성은 JWT 검증 기반을 제공하지만 회원가입·로그인·발급 API를 자동으로 만들어 주지는 않는다. 참고: [Spring Security JWT](https://docs.spring.io/spring-security/reference/servlet/oauth2/resource-server/jwt.html).

## 7. 내 정보 조회와 이름 변경 흐름

내 정보 조회:

1. 검증된 토큰에서 사용자 식별자를 얻는다.
2. 해당 회원을 조회한다.
3. 외부에 보여도 되는 정보만 DTO로 반환한다.

이름 변경:

1. 인증한 본인의 ID와 새 이름을 받는다.
2. 이름의 길이·빈 문자열 등 규칙을 검사한다.
3. 본인의 표시 이름을 트랜잭션 안에서 변경한다.
4. 변경된 정보를 반환한다.

요청 본문에 다른 회원 ID가 들어 있다고 그 회원의 이름을 바꾸지 않는다. 처리 기준은 인증 결과다. 소셜 전용 회원에게 일반 로그인 ID가 없을 수 있으므로 내 정보 응답의 선택 필드와 앱 호환도 정한다.

## 8. 내부 코드는 어떻게 나눌 것인가?

아래 명칭은 역할을 설명하기 위한 예시다.

| 계층 | 예시 구성요소 | 역할 |
|---|---|---|
| presentation | `MemberController`, `AuthController` | 요청·응답 변환 |
| application | SignUpService, LoginService, SocialLoginService, MemberService | 가입·일반/소셜 로그인·조회·변경 흐름 |
| domain | `Member`, 저장소·해싱·토큰 인터페이스 | 회원 규칙과 필요한 기능 계약 |
| infrastructure | JPA 저장소, 비밀번호 검증기, JWT 발급기, 제공자별 인증 어댑터 | DB와 외부 인증 기술 구현 |

복잡하지 않은 기능까지 불필요하게 많은 클래스로 나누지 않는다. 반대로 Controller 한 곳에 DB 조회·비밀번호·토큰·응답 처리를 모두 넣지도 않는다.

## 9. 다른 모듈과의 관계

member는 일반 인증 정보·소셜 계정 연결·회원 정보·토큰 정책을 관리한다. 다른 모듈에는 필요한 경우 회원 식별자와 권한 등 최소한의 정보만 전달한다.

- favorite는 인증된 회원 ID로 즐겨찾기 소유권을 판단한다.
- positioning은 인증 결과와 만료 시각으로 측정 연결을 시작·종료한다.
- place의 변경 기능은 인증된 사용자의 쓰기 권한을 검사한다.
- shared에는 공용 식별 정보나 오류 표현만 둔다.

토큰 검증기를 보안 필터에 연결하는 작업은 애플리케이션 설정에서 수행한다. shared가 member 내부를 직접 참조하고 member도 shared를 참조하는 순환 구조는 피한다.

다른 모듈에서 회원 존재 여부를 꼭 확인해야 한다면 `MemberQuery` 같은 공개 조회 기능을 검토한다. 모든 요청마다 같은 조회를 반복하는 것을 기본 규칙으로 만들지는 않는다.

## 10. 실패 상황과 처리

| 상황 | 처리 방향 |
|---|---|
| 필수값 누락·형식 오류 | 어떤 입력이 잘못됐는지 안내 |
| 로그인 ID 중복·소셜 연결 충돌 | 고유 제약 위반을 업무 오류로 변환 |
| 소셜 인증 실패·제공자 장애 | 잘못된 인증과 외부 장애를 구분, 회원 생성 금지 |
| 이메일 일치 | 자동 병합하지 않고 별도 회원·연결 정책 적용 |
| 잘못된 로그인 정보 | 일반적인 인증 실패 메시지 |
| 토큰 누락·만료·위조 | 401 등 인증 실패 |
| 토큰은 있으나 대상 회원이 없음 | 정의한 인증·회원 상태 정책으로 처리 |
| 본인 권한 밖의 변경 | 접근 거절 |
| DB 저장 실패 | 관련 DB 변경을 되돌리고 오류 반환 |

내부 SQL이나 비밀번호 검증 상세 내용을 응답에 노출하지 않는다.

## 11. 구현 전에 결정할 사항

- 일반 로그인 유지 범위와 기존 폼·내 정보 응답 호환.
- 확정: 이메일·전화번호 선택, 이메일 중복 허용. 표시 이름 수집과 기존 폼 호환은 가입 API에서 연결한다.
- 확정: 로그인 ID는 앞뒤 공백 제거 후 대소문자를 구분한다.
- 카카오·구글의 SDK·허용 앱/client·토큰 검증 방식.
- 계정 연결·해제 API의 초기 포함 여부와 마지막 로그인 수단 보호.
- JWT 키·만료·식별자와 기존 sub=userId 토큰의 호환.
- bcrypt 해시 호환·회원 상태 변경 후 기존 토큰 효력.
- 재발급·로그아웃·탈퇴의 범위와 데이터 정리 정책.

## 12. 완료 확인

- [ ] 일반 가입·로그인·내 정보·이름 변경이 합의한 형식으로 동작한다.
- [ ] 회원과 일반 인증 또는 소셜 연결이 부분 저장되지 않는다.
- [ ] 소셜 전용 회원이 가짜 비밀번호 없이 로그인한다.
- [ ] 동일 소셜 계정의 동시 최초 로그인을 일관되게 처리한다.
- [ ] 위조·만료·다른 앱용 인증 결과를 거절한다.
- [ ] 이메일 일치로 회원을 자동 병합하지 않는다.
- [ ] 연결 기능을 채택하면 타인 연결 탈취와 마지막 수단 제거를 차단한다.
- [ ] 응답·로그에 비밀번호·제공자 토큰·인가 코드가 남지 않는다.
- [ ] 기존 비밀번호·토큰·앱 응답 호환을 테스트한다.
- [ ] 클래스·메서드·중요 보안 판단의 설명을 남긴다.
