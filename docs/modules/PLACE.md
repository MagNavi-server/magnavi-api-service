# place — 장소 정보 모듈

최초 작성일: 2026-09-10 · 실내 조회 API 반영일: 2026-09-21 · 모델 매핑 내부 조회 반영일: 2026-09-22

현재 구현: Building·Floor·IndoorLocation·ModelLocationMapping의 JPA 매핑과 내부 저장소 4개를 구현했다. 건물별 층 번호, 모델 키·버전·코드의 고유성과 실제 FK를 검증했다. 모델 코드와 내부 PK는 분리하며 실제 모델 구역 매핑 데이터는 아직 등록하지 않았다. 4-1단계에서 건물·층·활성 장소 GET 7개와 PlaceController·PlaceQueryService·PlacePersistenceAdapter·PlaceReadRepository·조회 DTO를 구현했다. 4-2단계에서 ModelLocationQueryService·ModelLocationPersistenceAdapter로 모델 매핑 내부 조회를 구현했다. 네이버 연동은 후속 구현이다. [조회 API 안내](../api/PLACE_API.md)에 실행 순서와 요청·응답을 정리했다.

[전체 모듈 안내](README.md) · [Spring 구현 계획](../../IMPLEMENTATION_PLAN.md) · [DB 스키마](../../DATABASE_SCHEMA.md)

## 1. 무엇을 하는 모듈인가?

place는 “장소가 어디에 있고 어떤 곳인가?”를 알려 주는 모듈이다.

실내 장소·건물·층과 모델 코드 매핑은 직접 관리한다. 실외 장소 검색은 네이버 지역 검색 API를 호출해 앱에 전달한다. 직접 조사한 실외 장소·시설·접근성 정보가 필요하면 자체 관리 기능을 별도로 둔다.

앱은 지도를 표시하고 Spring은 검색을 중계한다. 검색 결과를 받는 것과 그 데이터를 우리 DB에 영구 저장하는 것은 다른 일이다. 이 모듈은 사용자 이동 이력을 저장하거나 위치를 직접 추론하지 않는다.

## 2. 장소 정보의 출처를 구분하자

| 개념 | 예시 | 관리 방식 |
|---|---|---|
| 건물·층·실내 장소 | A관 2층 205호 앞 | 자체 DB |
| 모델 코드 매핑 | 특정 모델 v1의 205 → 장소 31 | 자체 기준표 |
| 네이버 외부 검색 결과 | 검색한 업체·기관 | 외부 조회·전달, 전체 저장하지 않음 |
| 자체 실외 장소 — 선택 | 직접 조사한 정문 접근 경로 | 필요할 때 자체 DB |
| 시설 — 선택 | 직접 조사한 경사로 | 자체 장소에 연결 |

위 건물·장소명은 가상 예시다. 외부 업체 정보가 곧 우리가 검증한 접근성 정보는 아니다.

## 3. 구현할 기능과 전환 범위

| 기능 | 기존 경로 또는 구분 | 방향 |
|---|---|---|
| 건물 목록·상세 | GET /buildings, GET /buildings/{buildingId} | 4-1 구현 |
| 건물별 층 목록·층 상세 | GET /buildings/{buildingId}/floors, GET /floors/{floorId} | 4-1 구현 |
| 층별 장소 목록 | GET /floors/{floorId}/locations | 4-1 구현 |
| 실내 목록 | GET /locations/ | 4-1 구현 |
| 실내 상세 | GET /locations/{location_id} | 4-1 구현, 새 DB의 내부 장소 ID 사용 |
| 네이버 장소 검색 | 신규. GET /places/search?query=...는 경로 예시 | place의 검색 서비스로 구현 |
| 실외 등록·목록·상세·수정·삭제 | 기존 /outdoor-places/ 계열 | 자체 관리 필요성과 앱 호환에 따라 이관·보류 결정 |

네이버 검색을 도입했다고 기존 실외 장소 데이터나 API가 자동으로 없어지는 것은 아니다. 사용 중인 앱·시설 데이터의 보존과 전환을 확인해야 한다.

실내 장소 관리자용 등록·수정·삭제 API도 별도 결정 사항이다. 기준 데이터는 검증된 마이그레이션이나 관리 절차로 준비할 수 있다. 이번에는 실제 자료나 임의 예시를 개발/운영 DB에 등록하지 않았다. 모든 조회 GET은 기존 FastAPI처럼 로그인 없이 허용하며 변경 API는 제공하지 않는다.

## 4. 어떤 데이터를 관리하는가?

| 기본 테이블 | 주요 정보 |
|---|---|
| buildings | 건물 ID·이름·주소 |
| floors | 층 ID·건물 ID·층 번호 |
| indoor_locations | 장소 ID·층 ID·이름·설명·활성 여부 |
| model_location_mappings | 모델 키·버전·위치 코드·실내 장소 ID |

outdoor_places와 place_facilities는 자체 실외 장소·시설 관리를 선택할 때만 만든다. 네이버 검색을 실행할 때마다 이 테이블에 결과를 넣지 않는다.

컬럼·FK·고유 제약·선택 테이블의 적용 시점은 [DB 스키마](../../DATABASE_SCHEMA.md)가 기준이다.

## 5. 장소 목록·상세 조회 흐름

예시: 앱 사용자가 장소 목록을 열고 “A관 2층 205호 앞”을 선택한다.

목록 조회:

1. Controller가 목록 요청을 받는다.
2. 페이지 크기와 범위 등 요청 조건을 검사한다.
3. Service가 Repository에 조회를 요청한다.
4. Repository가 DB에서 해당 범위의 장소를 가져온다.
5. 응답 DTO로 변환해 목록을 반환한다.

상세 조회:

1. 앱이 선택한 장소 ID로 요청한다.
2. 해당 장소와 필요한 건물·층 정보를 조회한다.
3. 장소가 있으면 이름·층·설명 등을 반환한다.
4. 없으면 장소 없음 오류를 반환한다.

```text
장소 ID → 장소 조회 → 건물·층 등 필요한 정보 조합 → 상세 응답
```

현재 목록은 기존 skip·limit 형식의 배열 응답을 유지한다. skip은 기본 0·최대 10,000, limit은 기본/최대 100·최소 1이다. 건물·장소는 ID순, 층은 층 번호·ID순으로 정렬한다. 없는 부모는 404, 존재하지만 자식이 없는 부모는 빈 배열로 구분한다. 비활성 장소는 목록·상세에서 제외하며 실제 DB 행은 삭제하지 않는다. 끝의 슬래시 유무를 모두 지원한다.

## 6. 모델 위치 코드를 장소로 바꾸는 흐름

4-2단계의 내부 조회는 구현했다. 실제 Python 통신과 positioning 호출 연결은 후속 단계다. [내부 조회 안내](../api/MODEL_LOCATION_MAPPING.md)에 입력 제한·오류·검증을 정리했다.

향후 연결 예시: positioning이 선택한 모델 범위에서 버전 `v1`, 위치 코드 `205`를 전달받았다. 실제 매핑 키에는 model_key·model_version·location_code를 함께 사용한다.

1. positioning이 필요한 경우 place의 공개 조회 기능을 호출한다.
2. place는 모델 버전과 위치 코드에 맞는 매핑을 확인한다.
3. 매핑이 가리키는 실내 장소 정보를 조회한다.
4. 장소 ID와 표시 정보를 담은 DTO를 반환한다.
5. positioning이 필요한 정보만 앱 결과에 붙이거나, 앱이 별도 장소 API로 조회한다.

```text
모델 v1 / 코드 205
  → place의 매핑 조회
  → 실내 장소 ID 31
  → A관 / 2층 / 205호 앞
```

모델 코드와 DB PK가 우연히 같은 숫자일 수 있지만 같은 개념으로 가정하지 않는다. DB PK가 바뀌거나 다른 건물이 추가되어도 매핑이 잘못 연결되지 않아야 한다.

매핑 키에는 모델 범위·버전·코드를 모두 사용한다. 대소문자·공백·앞자리 0을 보존하며, 누락·비활성 장소는 NOT_FOUND로 처리한다. 없는 코드를 임의로 0번 장소나 다른 버전에 연결하지 않는다. 현재 성공 조회는 SQL 2회이고 자체 캐시는 없다.

센서가 들어올 때마다 장소 DB를 다시 조회할 필요는 없다. 별도 장소 조회 API나 검증된 캐시를 사용할 수 있으며, 캐시를 쓰면 매핑 갱신 시 만료·교체 정책도 함께 정한다.

## 7. 실외 검색과 선택적 자체 관리

### 7.1 네이버 검색 흐름

1. 앱이 검색어를 Spring에 보낸다.
2. Controller가 검색어 길이·허용 파라미터·요청 한도를 검사한다.
3. PlaceSearchService가 네이버 호출 어댑터에 검색을 요청한다.
4. 어댑터가 서버 설정의 인증 정보로 API를 호출한다.
5. 응답의 표시 형식·좌표를 앱 계약에 맞게 처리한다.
6. 앱에 반환하고 앱이 지도에 표시한다. 기본 DB 저장은 없다.

NaverLocalSearchClient 같은 이름은 외부 API 호출 구현의 예시다. 검색용 Client Secret을 앱에 전달하지 않는다.

검색 요청은 긴 DB 트랜잭션으로 감싸지 않는다. 호출 시간 제한·한도·재시도 횟수를 제한하고, 제공자 장애를 “검색 결과 없음”으로 숨기지 않는다. 원문 검색어와 응답 전체를 기본 로그에 남기지 않는다.

### 7.2 API에서 확인한 제약

신규 신청은 NAVER API HUB 기준으로 진행한다. 기존 개발자센터의 Search API 신규 신청은 2026-07-31부터 중단되었다. [공식 공지](https://developers.naver.com/notice/article/32530)

2026-09-10 확인한 지역 검색 명세는 결과 최대 5개·start=1이며 고유 장소 ID 필드가 없다. 네이버 지도 앱과 같은 전체 검색·페이지 이동 기능을 보장하지 않는다. [현재 지역 검색 명세](https://api.ncloud-docs.com/docs/naver-api-hub-search-local)

좌표 단위·축·표현은 실제 응답으로 검증하고 오래된 예제의 변환 공식을 무조건 재사용하지 않는다. 검색 결과의 표시·변환도 적용되는 이용 조건을 확인한다.

### 7.3 검색 결과를 저장하는가?

기본 검색은 조회·전달만 한다. 캐시나 즐겨찾기 스냅샷은 허용 필드·기간·갱신·표시 조건 확인 후 별도 구현한다. 영구 저장이 가능하다고 아직 확정하지 않았다.

존재하지 않는 naver_place_id를 만들어 공식 ID처럼 취급하거나, URL에서 추출한 숫자를 안정적인 장소 ID로 간주하지 않는다. 외부 즐겨찾기 식별은 [favorite 문서](FAVORITE.md)와 DB 스키마의 결정 항목을 따른다.

### 7.4 자체 실외 장소 CRUD — 선택

필요하다면 기존 POST·GET·PATCH·DELETE /outdoor-places/ 계열을 이관한다.

- 등록: 쓰기 권한 → 입력·좌표 확인 → 장소와 시설을 같은 트랜잭션으로 저장.
- 수정: 권한·존재 확인 → 변경 필드 검사 → 변경 저장.
- 삭제: 권한·참조 확인 → 합의한 삭제 거절·비활성화 또는 물리 삭제.

PATCH의 필드 누락은 기존 값 유지, 명시적 null은 제거 등으로 의미를 합의한다. 참조 중인 장소를 무조건 삭제하지 않는다. place가 favorite 내부 테이블을 직접 수정해 사용자 항목을 임의 삭제하지도 않는다.

## 8. 검증할 규칙

- 실내 장소의 건물·층 참조와 모델 코드 매핑.
- 장소명·주소·설명 길이와 페이지 최대 크기.
- 외부 검색어·파라미터·호출 빈도·응답 대기 시간.
- 네이버 인증 정보의 서버 보관과 원문 로그 제외.
- 캐시·즐겨찾기 저장이 허용되는 범위.
- 자체 장소를 관리한다면 좌표 범위·변경 권한·시설 관계·삭제 정책.

자체 좌표는 위도 -90~90, 경도 -180~180의 유한한 수치여야 한다. 접근성 정보의 조사 시점·갱신 책임도 정한다.

## 9. 내부 코드와 다른 모듈의 사용

| 계층 | 예시 구성요소 | 역할 |
|---|---|---|
| presentation | PlaceController·LocationResponse·PlaceExceptionHandler | 조회 GET·기존 응답 필드 변환·안전한 오류 |
| application | PlaceQueryService·ModelLocationQueryService, 후속 PlaceSearchService·선택적 PlaceCommandService | ID·모델 코드 내부 조회, 후속 외부 검색·변경 |
| domain | 건물·층·장소·시설·매핑 | 장소 규칙 |
| infrastructure | PlacePersistenceAdapter·ModelLocationPersistenceAdapter·PlaceReadRepository·기존 JPA 저장소 | 읽기 전용 트랜잭션·모델 매핑·JPQL JOIN 조회. 네이버 어댑터는 후속 |

다른 모듈에 공개할 기능의 예:

| 공개 기능 예시 | 호출하는 쪽 | 반환할 내용 |
|---|---|---|
| `PlaceQueryService.getLocation(locationId)` | favorite 등에서 향후 사용 가능 | 활성 장소와 건물·층을 담은 IndoorLocationInfo |
| `ModelLocationQueryService.findLocation(modelKey, modelVersion, locationCode)` | positioning에서 향후 사용 가능 | 활성 장소와 건물·층을 담은 IndoorLocationInfo |

PlaceQueryService의 ID 기반 조회와 ModelLocationQueryService의 모델 코드 조회를 구현했다. positioning과의 실제 호출 연결은 후속 단계다. 다른 모듈에는 읽기 결과 DTO를 반환하고, 내부 JPA 엔티티나 수정용 Repository를 넘기지 않는다.

네이버 응답 객체를 favorite나 앱에 기술 의존성 그대로 퍼뜨리지 않는다. 필요한 검색 결과 DTO와 선택 정보의 검증 규격을 공개한다. 외부 결과에 내부 장소 FK가 있다고 가정하지 않는다.

장소별 회원 즐겨찾기 여부는 place 자체의 장소 정보와 구분한다. 필요한 화면 조합은 호출하는 업무 흐름에서 구성해 모듈의 상호 의존을 줄인다.

## 10. 실패 상황과 완료 확인

| 상황 | 처리 방향 |
|---|---|
| 없는 내부 장소·모델 매핑 | 대상 없음 상태, 임의 장소로 대체하지 않음 |
| 검색 결과 없음 | 정상적인 빈 결과 |
| 네이버 장애·시간 초과·제공자 한도 | 검색 장애로 구분, 무제한 재시도 금지 |
| 외부 저장 정책 미확정 | 검색은 제공하되 해당 영구 저장은 보류 |
| 잘못된 입력·좌표 | 입력 오류 |
