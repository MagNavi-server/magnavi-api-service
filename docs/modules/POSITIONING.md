# positioning — 실시간 위치 연결 모듈

작성일: 2026-09-10 · 상태: 구현 예정 설계

[전체 모듈 안내](README.md) · [장소 모듈](PLACE.md) · [Spring 구현 계획](../../IMPLEMENTATION_PLAN.md) · [DB 스키마](../../DATABASE_SCHEMA.md)

## 1. 무엇을 하는 모듈인가?

positioning은 앱의 센서를 모델 서비스로 보내고, 돌아온 위치 결과를 해당 앱 연결로 전달한다.

쉽게 말하면 “측정 연결을 관리하는 중계 담당자”다. 위치를 직접 계산하는 모델은 Python 서비스에 남긴다.

이 모듈의 핵심은 단순 전달만이 아니다. 누가 연결했는지 확인하고, 연결별 메시지를 구분하며, 너무 많은 입력이나 끊어진 연결을 안전하게 처리해야 한다.

## 2. 맡는 일과 맡지 않는 일

| 맡는 일 | 맡지 않는 일 |
|---|---|
| 인증된 앱의 실시간 연결 관리 | 회원가입·비밀번호 확인 |
| 센서 메시지의 형식·순서 검사 | 모델 학습·추론 알고리즘 구현 |
| 모델 서비스로 센서 전달 | 모델용 16개 샘플 버퍼 관리 |
| 결과를 원래 앱 연결로 전달 | 장소 기준 데이터 수정 |
| 연결 한도·대기열·종료·재접속 처리 | 센서 원본·예측 이력 DB 저장 |

센서와 예측 결과는 처리 중 메모리에 잠시 존재할 수 있지만, 이력 테이블로 저장하지 않는다. 일반 운영 로그에도 센서 원본과 상세 위치 결과를 남기지 않는다.

## 3. 전체 연결 구조

```text
앱
  ↕ WebSocket: 앱과 Spring 사이의 지속 연결
Spring positioning
  ↕ 양방향 gRPC 스트리밍: Spring과 모델 서비스 사이의 지속 호출
Python 모델 서비스
```

WebSocket은 앱과 서버가 연결을 유지하면서 양쪽으로 메시지를 주고받는 방식이다.

양방향 gRPC 스트리밍은 하나의 RPC 호출 안에서 요청 메시지와 응답 메시지를 계속 주고받는 방식이다. RPC는 다른 서버의 기능을 호출한다는 뜻이다.

Spring은 이번 연동에서 gRPC 클라이언트다. 모델 서버를 호출하기 위해 Spring에 gRPC 서버 역할까지 추가할 필요는 없다.

기존 `POST /predict`를 센서 한 건마다 호출하던 방식은 실시간 연결로 전환한다. WebSocket 경로와 메시지 규격은 아직 확정 전이며, 기존 REST API와 자동으로 호환되지는 않는다.

## 4. 회원과 측정 세션은 어떻게 다른가?

회원은 계정이고, 측정 세션은 한 번의 측정 연결이다. 일반·카카오·구글 로그인 중 무엇을 사용했는지가 아니라 MagNavi 내부 member_id로 회원을 구분한다. 제공자 토큰을 측정 연결 인증에 그대로 사용하지 않는다.

예를 들어 같은 사람이 앱을 종료했다가 다시 열어도 회원은 그대로지만 측정 연결은 새로 시작된다.

| 상황 | 회원 ID | 측정 세션 |
|---|---|---|
| A가 처음 측정 | 101 | 세션 A-1 |
| A가 종료 후 다시 측정 | 101 | 세션 A-2 |
| B가 동시에 측정 | 202 | 세션 B-1 |

세션 이름은 설명용 예시다. 실제 세션 ID는 서버가 충돌하지 않도록 발급한다.

```text
앱 A 연결 → 세션 A-1 → gRPC 스트림 A → 앱 A로 결과
앱 B 연결 → 세션 B-1 → gRPC 스트림 B → 앱 B로 결과
```

세션을 회원 ID 하나로만 구분하면 재접속 전후나 여러 기기의 연결이 섞일 수 있다. 같은 회원의 동시 측정을 허용할지는 별도의 제한 정책으로 정한다.

gRPC 채널은 모델 서버로 가는 통신 기반이다. 채널은 재사용하되, 측정 세션마다 독립된 스트리밍 호출을 만든다. 하나의 채널을 재사용한다는 이유로 모든 사용자의 센서를 하나의 스트림에 합치지 않는다.

## 5. 연결을 시작하는 흐름

1. 앱이 WebSocket 연결을 요청한다.
2. 인증 계층이 MagNavi 서비스 토큰과 만료 시각을 확인한다.
3. positioning이 사용자별·서버별 연결 한도를 검사한다.
4. 서버가 새 측정 세션을 만들고 앱 연결과 연결한다.
5. 해당 세션의 gRPC 스트리밍 호출을 시작한다.
6. 합의한 준비 상태가 확인되면 앱에 센서 전송 가능 상태를 알린다.

인증 전에는 모델 스트림을 열거나 센서를 처리하지 않는다.

네트워크 연결이 열렸다고 모델도 정상 준비되었다고 단정하지 않는다. 모델 준비 실패와 연결 실패를 앱에 구분해서 안내할 수 있도록 계약을 정한다.

앱의 WebSocket 라이브러리가 인증 헤더를 지원하는지 먼저 확인한다. 지원하지 않으면 짧은 수명의 연결 티켓 같은 방식을 검토한다. 장기 JWT를 URL에 넣어 로그에 남기는 것을 기본 방식으로 삼지 않는다.

## 6. 센서 한 개가 들어오면 어떻게 처리하는가?

예시: 앱이 샘플 순번 17의 센서값을 보낸다.

1. 아직 활성 상태인 측정 세션인지 확인한다.
2. 메시지 크기와 필수 필드, 숫자 형식을 검사한다.
3. 샘플 순번·측정 시간·전송 빈도 규칙을 확인한다.
4. 해당 세션의 제한된 전달 경로에 입력을 넣는다.
5. 순서를 유지하며 gRPC 요청 메시지로 변환해 보낸다.
6. 다음 센서를 받으면서 모델 응답도 별도로 처리한다.

검사할 대표 입력은 자기장 3축, 방향 3축, 순번, 측정 시간이다. 축의 의미와 단위는 통신 계약에서 확정한다.

숫자 0은 정상값일 수 있다. 값이 누락된 것과 0이 들어온 것을 구분해야 한다. NaN과 무한대는 정상적인 센서 수치로 받아들이지 않는다.

메시지 형식 검증은 Spring이 담당한다. 모델에 넣기 위한 필터링·정규화·특징 추출은 Python이 담당한다.

### 6.1 16개를 앱에서 모아서 보내는 것인가?

아니다. 앱은 센서를 측정하는 대로 보낸다.

```text
앱:       샘플 1 → 샘플 2 → 샘플 3 → ... → 샘플 16 → 샘플 17
Spring:   받는 대로 각 세션의 스트림으로 전달
Python:   해당 스트림의 모델 입력을 모으고 준비 상태에 따라 추론
```

연속 전송은 앱의 16개 묶음 전송을 뜻하지 않는다. 다만 모델이 요구하는 정보가 충분히 모이는 시간이나 계산·네트워크 시간까지 없애 주지는 않는다.

16개가 모이기 전의 결과를 제공할지, 워밍업 상태만 보낼지는 모델 계약으로 확정한다. 현재 모델의 초기 보완 동작을 그대로 유지할지도 이때 확인한다. 결과 개수와 추론 주기 역시 계약을 따르며, 센서 한 개마다 반드시 예측 한 개가 나온다고 가정하지 않는다.

### 6.2 Spring의 대기열과 Python의 버퍼는 다른가?

| 구분 | 목적 | 담당 |
|---|---|---|
| 전달 대기열 | 통신 상대가 잠시 느릴 때 전송할 메시지를 제한적으로 대기 | Spring |
| 모델 입력 버퍼 | 추론에 필요한 최근 샘플 묶음을 구성 | Python |

Spring 대기열은 16개를 모으는 기능이 아니다. 전송 지연을 흡수하기 위한 작은 대기 공간이며, 길이와 대기 시간에 제한을 둔다.

## 7. 결과가 돌아오면 어떻게 처리하는가?

1. 결과가 어느 스트림에서 왔는지 확인한다.
2. 연결된 세션이 아직 활성 상태인지 확인한다.
3. 예측·워밍업·오류 등 메시지 종류를 구분한다.
4. 예측이면 순번·모델 버전·위치 코드·점수 등을 앱 형식으로 변환한다.
5. 장소 정보가 필요하면 place의 공개 조회 기능으로 코드를 해석한다.
6. 해당 세션의 앱 연결에만 순서대로 보낸다.

예시: 모델 v1의 위치 코드 205가 돌아오면 place가 관리하는 매핑을 통해 “A관 2층 205호 앞”으로 해석할 수 있다. 이 코드와 장소명은 설명용 예시다.

장소 상세 정보는 앱이 따로 조회하도록 정할 수도 있다. 서버가 붙여 보내기로 해도 매 센서마다 DB를 조회하지 않는다. 필요하다면 모델·지도 버전 기준의 매핑 조회와 캐시 갱신 규칙을 설계한다.

매핑되지 않는 코드를 임의의 장소로 바꾸지 않는다. 모델 점수도 실제 정답 확률이 보장된 값처럼 표현하지 않는다.

## 8. 어떤 정보를 메모리에서 관리하는가?

| 정보 | 필요한 이유 |
|---|---|
| 세션 ID·회원 식별자 | 연결과 권한을 구분 |
| 앱 연결·gRPC 호출 참조 | 입력과 결과의 목적지를 연결 |
| 인증 만료 시각 | 오래 열린 연결의 만료 처리 |
| 마지막 활동 시간 | 멈춘 연결 정리 |
| 마지막 샘플 순번 | 중복·역순 입력 검사 |
| 상태·종료 여부 | 종료된 연결의 메시지 차단 |
| 제한된 입력·결과 대기열 | 느린 상대에 대한 자원 보호 |

초기 상태 흐름은 다음과 같이 제안한다.

```text
인증 확인 → 연결 준비 → 측정 중 → 종료 중 → 종료
                 └─ 준비 실패 ────────→ 종료
```

연결 상태를 관리하려고 DB 테이블을 새로 만드는 것은 기본 계획에 포함하지 않는다. 여러 Spring 인스턴스를 운영할 경우 연결과 전역 한도 관리 방식은 별도로 설계한다.

## 9. 비동기 처리와 과부하는 어떻게 다루는가?

비동기 gRPC 클라이언트는 모델 응답을 기다리는 동안 요청 처리 스레드를 계속 붙잡아 두지 않고, 응답이 도착했을 때 콜백으로 처리하게 한다. 콜백은 “결과가 왔을 때 실행할 함수”다.

이것은 모델 계산 자체를 빨라지게 한다는 뜻이 아니다. 여러 연결을 기다리는 자원을 효율적으로 쓰는 데 도움이 된다.

MVC를 모두 WebFlux로 바꾸거나 모든 메서드에 `@Async`를 붙일 필요는 없다. 현재 버전에 맞는 비동기 stub과 콜백 경로를 명시적으로 구성한다. stub은 생성된 gRPC 호출용 클라이언트 객체다. 참고: [Spring gRPC 클라이언트](https://docs.spring.io/spring-grpc/reference/client.html).

입력 속도가 처리 속도보다 계속 빠르면 대기열이 늘어나므로 다음 제한이 필요하다.

- 사용자별·인스턴스별 활성 연결 수.
- 메시지 크기와 센서 전송 빈도.
- 입력·결과 대기열 길이와 최대 대기 시간.
- 연결 준비 시간, 무응답 시간, 측정 연결의 최대 수명.

“상대가 받을 수 있을 때 보낸다”는 흐름 제어와 애플리케이션의 대기열 제한을 함께 적용한다. 비동기라고 작업을 무제한으로 생성해서는 안 된다. 참고: [gRPC 흐름 제어](https://grpc.io/docs/guides/flow-control/).

같은 스트림의 입력 송신과 같은 WebSocket 연결의 결과 송신은 각각 직렬화한다. 여러 콜백이 동시에 같은 연결에 쓰지 않도록 전송 경로를 정한다. 긴 DB 조회나 느린 앱 송신으로 gRPC 콜백을 오래 막지 않는다. 참고: [Spring WebSocket API](https://docs.spring.io/spring-framework/reference/web/websocket/server.html).

초기에는 한도를 지속 초과하면 오류를 알리고 연결을 정리하는 정책을 제안한다. 센서를 조용히 버리고 정상인 것처럼 계속 처리하지 않는다. 일부 결과만 최신 값으로 합치는 정책이 필요하다면 앱과 별도로 합의한다.

서버가 여러 대라면 각 서버의 메모리 제한만으로 사용자 전체 연결 한도를 보장할 수 없다. 분산 제한 저장소가 필요한지는 배포 규모가 정해진 뒤 결정한다.

## 10. 종료·오류·재접속 흐름

앱 종료, 토큰 만료, 무응답, 모델 오류, 한도 초과가 종료 원인이 될 수 있다.

1. 세션을 종료 중으로 바꾸고 새 입력을 거절한다.
2. 더 이상 결과를 앱에 전달하지 않도록 표시한다.
3. 대응 gRPC 호출을 취소하고 앱 연결을 정리한다.
4. 대기열과 연결 참조를 해제한다.
5. 종료 사유와 집계 지표만 남긴다.

종료 요청이 여러 곳에서 동시에 들어와도 한 번 정리한 것과 같은 결과가 나도록 구현한다. 이를 멱등적인 종료라고 한다.

모델 호출을 취소해도 이미 시작한 계산이 즉시 중단된다고 보장할 수는 없다. 늦게 돌아온 결과는 종료 상태와 세션 식별자를 확인해 전달하지 않는다.

재접속은 새 세션으로 시작한다. 이전 세션의 센서를 무조건 다시 보내거나, 이전 결과를 새 연결로 전달하지 않는다. 앱 재시도 간격·횟수도 제한해 모델 장애 때 연결 시도가 폭증하지 않게 한다.

장시간 스트림에 짧은 단건 요청 제한 시간을 그대로 적용하지 않는다. 전체 연결 수명, 마지막 메시지 이후의 무응답 시간, 개별 작업의 대기 시간은 다른 개념이다.

## 11. 내부 구성과 다른 모듈의 관계

명칭은 구현 방향을 설명하기 위한 예시다.

| 계층 | 예시 구성요소 | 역할 |
|---|---|---|
| presentation | WebSocket 핸들러·메시지 DTO | 연결 이벤트와 앱 메시지 수신·변환 |
| application | `PositioningSessionService` | 연결 시작·센서 전달·결과 전달·종료 조정 |
| domain | 세션 상태·센서 값·상태 전이 규칙 | 연결별 규칙 표현 |
| application의 외부 호출 계약 | `ModelStreamClient` | 모델에 필요한 호출 기능 정의 |
| infrastructure | 비동기 gRPC 어댑터·메모리 세션 저장소 | 실제 스트림과 연결 자원 관리 |

네트워크 연결 객체와 생성된 gRPC 메시지를 모든 계층에 퍼뜨리지 않는다. 세션의 상태 규칙과 실제 소켓·콜백 처리를 구분한다.

member의 인증 결과는 보안 연결 설정을 통해 전달받는다. 필요한 장소 매핑은 place의 공개 조회 기능을 호출한다. 네이버 외부 검색은 별도 업무 흐름이며 실내 모델 코드 매핑을 대신하지 않는다. 매 센서나 예측 결과마다 네이버 검색을 호출하지 않는다. 다른 모듈의 회원·장소 테이블을 직접 변경하지 않는다.

측정 연결 전체에 DB 트랜잭션을 걸지 않는다. 네트워크로 이미 보낸 메시지는 DB 롤백으로 회수할 수 없고, 장시간 DB 연결을 점유해서도 안 된다.

## 12. 실패 상황과 테스트

| 상황 | 기대 동작 |
|---|---|
| 인증 실패 | 센서 처리·모델 호출 전에 거절 |
| 잘못된 형식·순번·수치 | 계약에 맞는 입력 오류 처리 |
| 모델 준비 실패 | 준비 실패 안내와 세션 정리 |
| 워밍업 결과 | 예측으로 꾸미지 않고 상태로 전달 |
| A·B 동시 측정 | 각자의 연결로만 결과 전달 |
| 앱 수신 지연·모델 지연 | 대기열 제한과 과부하 정책 적용 |
| 앱 종료·토큰 만료 | 대응 호출 취소와 자원 해제 |
| 종료 후 늦은 결과 | 이전 세션 결과 폐기 |
| 모델 서버 장애 | 실시간 실패 처리, 독립 REST 기능은 계속 사용 |

먼저 가짜 모델 서비스로 정상·지연·오류·취소를 재현한다. 이후 실제 모델과 연결해 여러 앱 대체 클라이언트의 지연·자원 사용을 측정한다.

평균 지연뿐 아니라 p95·p99도 본다. 예를 들어 p95는 관찰한 요청의 95%가 그 시간 이내에 처리됐다는 뜻이다. 앱과 서버 시계가 같다고 가정하지 않고 서버 내부 지연과 앱에서 체감하는 전체 지연을 구분한다.

## 13. 구현 전에 결정할 사항

- WebSocket 경로, 인증 전달 방법, 이벤트 형식.
- gRPC 계약의 단일 원본·버전·생성 방식.
- 센서 단위·축·측정 시간·순번·누락·재접속 규칙.
- 워밍업 응답과 예측 주기.
- 장소 상세를 결과에 포함할지, 앱에서 따로 조회할지.
- 동시 사용자·샘플 빈도·허용 지연·대기열 크기.
- 같은 회원의 동시 측정 허용 수.
- 토큰 만료·최대 연결 수명·과부하·재시도 정책.
