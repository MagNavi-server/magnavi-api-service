# Spring 모듈 안내서

작성일: 2026-09-10 · 기반 구현 반영일: 2026-09-18

이 폴더는 MagNavi Spring 서버를 모듈러 모놀리스로 구현하기 위한 설명서다. 처음 읽는 사람도 기능과 처리 흐름을 이해할 수 있도록 작성했다.

초기에는 아래 계층을 위한 빈 클래스 39개를 준비했다. 이후 공통 오류·요청 추적·기본 보안과 실행·테스트 설정을 구현했으며, 2단계에서는 8개 업무 엔티티·JPA 저장소와 Flyway SQL 3개를 구현했다. 3-1단계에서 일반 회원·JWT, 4-1단계에서 건물·층·활성 장소 조회, 4-2단계에서 모델 코드 매핑 내부 조회를 구현했다. 네이버 검색·소셜 인증·다른 업무 API·실시간 연동은 후속 작업이다. 전체 작업 순서는 [Spring 구현 계획](../../IMPLEMENTATION_PLAN.md), 현재 실행 방법은 [README](../../README.md), 테이블·컬럼·저장 정책은 [DB 스키마 설계](../../DATABASE_SCHEMA.md)를 참고한다.

## 1. 모듈러 모놀리스는 무엇인가?

모듈러 모놀리스는 **하나의 서버 프로그램 안에서 기능을 책임별로 나눈 구조**다.

예를 들어 하나의 도서관 안에 회원 데스크, 자료 안내 데스크, 대출 데스크가 있는 것과 비슷하다. 같은 건물에서 일하지만 각 데스크가 관리하는 정보와 맡은 일이 다르다.

MagNavi에서도 Spring 애플리케이션은 하나로 실행한다. 그 안에서 회원, 장소, 즐겨찾기, 실시간 연결의 책임을 나눈다.

- 모듈마다 별도 서버나 GitHub 레포를 만들 필요는 없다.
- 모듈끼리는 보통 Java 메서드를 호출한다.
- 모듈 사이의 호출에 HTTP나 gRPC를 추가하지 않는다.
- Python 모델 서비스처럼 별도 서버를 호출할 때 gRPC를 사용한다.
- 하나의 DB를 사용하더라도 테이블을 관리하는 책임은 모듈별로 정한다.

폴더만 나누고 다른 모듈의 내부 코드와 테이블을 자유롭게 수정하면 경계가 약해진다. 어떤 기능을 외부에 공개하고, 어떤 데이터는 자기 모듈 안에서만 바꿀지 정하는 것이 중요하다.

여기서 말하는 구조는 설계 방식이다. Spring Modulith 같은 특정 라이브러리 도입까지 확정한 것은 아니다.

## 2. 모듈별 문서

| 문서 | 맡은 일 | 먼저 떠올릴 질문 |
|---|---|---|
| [member](MEMBER.md) | 회원·일반/카카오/구글 로그인 | “이 사용자는 누구인가?” |
| [place](PLACE.md) | 실내 장소·모델 매핑·네이버 검색 | “이 장소는 어디이며 어떤 정보가 있는가?” |
| [favorite](FAVORITE.md) | 개인 즐겨찾기 | “이 사용자가 저장한 대상은 무엇인가?” |
| [positioning](POSITIONING.md) | 실시간 측정 연결 | “이 센서의 결과를 어느 연결로 보내야 하는가?” |
| [shared](SHARED.md) | 최소 공통 코드 | “여러 모듈에서 공통으로 표현할 것은 무엇인가?” |

`shared`는 회원이나 장소처럼 독립된 업무 기능을 제공하는 모듈이 아니라 공통 지원 영역이다.

추천 읽기 순서는 이 안내서 → member → place → favorite → positioning → shared다.

## 3. 한 요청은 어떻게 이동하는가?

일반적인 REST 요청은 다음 흐름으로 처리한다.

```text
앱 요청
  → 인증 확인
  → Controller: 요청 형식 확인
  → Service: 업무 흐름 실행
  → Domain: 업무 규칙 확인
  → Repository: 필요한 DB 조회·저장
  → 응답 DTO 생성
  → 앱 응답
```

이 그림의 모든 단계를 항상 별도 클래스로 만들어야 한다는 뜻은 아니다. 네이버 검색처럼 DB 대신 외부 API를 호출하는 요청도 있다. 검색 결과 전체를 DB에 넣는다는 뜻이 아니다. 중요한 것은 역할이 섞이지 않게 구성하는 것이다.

실시간 센서는 연결이 유지되므로 별도 흐름을 사용한다.

```text
인증한 앱의 WebSocket 연결
  ↔ positioning의 측정 세션
  ↔ gRPC 클라이언트
  ↔ 외부 모델 서비스
```

## 4. 공통 용어를 먼저 이해하자

| 용어 | 쉬운 설명 |
|---|---|
| 모듈 | 관련된 기능과 규칙을 모아 놓은 영역 |
| presentation | 앱 요청을 받고 응답 형식으로 바꾸는 입구 |
| application | 가입·등록·삭제 같은 업무 순서를 실행하는 곳 |
| domain | 회원·장소·즐겨찾기의 의미와 규칙을 표현하는 곳 |
| infrastructure | DB나 외부 서버와 실제로 연결하는 코드 |
| Controller | HTTP 요청을 받는 클래스 |
| Service | 하나의 업무 흐름을 실행하는 클래스 |
| Repository | 데이터를 조회·저장하는 창구 |
| DTO | 요청·응답·모듈 간 전달에 필요한 값만 담은 객체 |
| 공개 인터페이스 | 다른 모듈에서 사용해도 된다고 정한 메서드 목록 |
| 트랜잭션 | 관련 DB 변경을 함께 성공시키거나 함께 되돌리는 범위 |
| PK | 테이블의 행 하나를 구분하는 고유 번호 |
| FK | 다른 테이블의 행을 가리키는 참조 |
| 멱등 처리 | 같은 요청을 여러 번 받아도 의도한 최종 상태가 같도록 처리하는 것 |

“공개 인터페이스”는 반드시 인터넷에 공개한 API를 뜻하지 않는다. 이 문서에서는 같은 Spring 프로그램 안의 다른 모듈이 호출하는 Java 기능도 포함한다.

## 5. 모듈끼리 어떤 정보를 주고받는가?

| 요청하는 쪽 | 제공하는 쪽 | 주고받을 내용 |
|---|---|---|
| 인증 연결 설정 | member | 토큰 검증에 필요한 정책·설정 연결 |
| favorite | place | 내부 장소 존재 여부와 표시 정보 |
| positioning | place | 모델 버전·위치 코드에 맞는 장소 조회, 필요할 때만 |
| 각 모듈 | shared | 공통 오류 형식, 인증 주체를 나타내는 최소 정보, 시각 같은 공용 도구 |

인증된 요청에는 MagNavi 내부 회원 식별자와 필요한 권한 정보가 전달된다. 일반·카카오·구글은 로그인 수단이며 favorite와 positioning이 제공자별 회원 체계를 따로 갖지 않는다. favorite와 positioning이 매 요청·매 샘플마다 회원 테이블을 직접 조회하는 구조를 기본으로 삼지 않는다.

공통 보안 필터와 각 모듈을 연결하는 코드는 애플리케이션의 조립 지점에서 설정한다. 예를 들어 루트의 `config/`에서 연결할 수 있다. 이 조립 지점은 새로운 업무 모듈이 아니다.

## 6. 데이터 소유권

| 영역 | 관리할 데이터 |
|---|---|
| member | members·local_credentials·social_accounts, 선택적 토큰 재발급 정보 |
| place | 건물·층·실내 장소·모델 매핑, 네이버 검색 중계, 선택적 자체 실외 장소·시설 |
| favorite | 내부 회원별 즐겨찾기·실제 내부 FK·조건부 외부 스냅샷 |
| positioning | 메모리의 측정 연결·대기열·상태, 센서 이력 DB 없음 |
| shared | 별도의 업무 테이블 없음 |

DB에 외래 키가 있다고 다른 모듈의 Repository를 직접 호출해도 된다는 뜻은 아니다. 예를 들어 favorite는 회원 ID를 참조하지만 회원 이름을 직접 수정하지 않는다.

데이터를 바꾸는 규칙은 소유 모듈이 관리한다. 다른 모듈은 공개된 기능을 호출하거나 필요한 조회 결과를 전달받는다.

## 7. 함께 지킬 설계 원칙

- 새 기능은 먼저 어느 모듈의 책임인지 정한다.
- 다른 모듈의 내부 JPA 엔티티를 그대로 응답이나 전달 객체로 사용하지 않는다.
- 서로를 순환해서 호출하는 구조를 만들기 전에 책임 배치를 검토한다.
- 여러 모듈에서 쓴다는 이유만으로 업무 코드를 모두 shared로 옮기지 않는다.
- DB 트랜잭션은 업무 범위에 적용하고 WebSocket 연결 전체를 감싸지 않는다.
- 센서 원본과 예측 이력은 DB·일반 운영 로그에 보관하지 않는다.
- 이메일 일치로 소셜 계정을 자동 연결하지 않는다.
- 네이버 검색과 자체 장소 저장을 구분하고 외부 저장 허용 조건을 먼저 확인한다.
- 클래스·메서드에는 역할을, 중요한 코드는 판단 이유를 주석으로 남긴다.
- 문서의 예시 명칭과 정책은 구현 전에 확정한다.

## 8. 문서를 어떻게 관리할 것인가?

[프로젝트 개요](../../PROJECT_OVERVIEW.md)는 서비스 역할을, [구현 계획](../../IMPLEMENTATION_PLAN.md)은 작업 순서를, [DB 스키마](../../DATABASE_SCHEMA.md)는 테이블·관계·저장·이관 정책을 다룬다. 이 폴더는 각 모듈의 기능과 동작을 자세히 설명한다. 스키마 상세를 바꾸면 모듈의 책임·흐름도 함께 갱신한다.

새 기능이 추가되면 해당 모듈 문서의 책임·흐름·데이터·오류·테스트 항목을 함께 갱신한다. 아직 정하지 않은 정책은 확정된 기능과 구분해서 표시한다.

## 9. 초기 골격과 현재 구현 상태

| 영역 | 초기 빈 클래스 수 | 대표 클래스 |
|---|---|---|
| member | 14 | Member, SignUpService, SocialLoginService, MemberPersistenceAdapter |
| place | 10 | IndoorLocation, PlaceQueryService, PlaceSearchService, NaverLocalSearchClient |
| favorite | 4 | Favorite, FavoriteService, FavoritePersistenceAdapter |
| positioning | 5 | PositioningSession, PositioningSessionService, GrpcModelStreamClient |
| shared | 3 | ErrorResponse, AuthenticatedMember, TraceIdGenerator |
| config | 3 | SecurityConfig, WebSocketConfig, GrpcClientConfig |

위 표는 초기 골격의 수다. 이후 member·place·favorite의 도메인 8개를 JPA 엔티티로 구현하고 각 모듈 infrastructure/persistence에 저장소 8개를 추가했다. 일반 회원 서비스·API·MemberPersistenceAdapter는 3-1단계에서 구현했다. 4-1단계에서 장소 조회 API·서비스·어댑터와 JPQL 조회 저장소도 구현했다. 외부 검색·즐겨찾기·positioning은 빈 골격으로 남아 있다. 선택 사항인 자체 실외 장소·시설 클래스는 미리 만들지 않았다.

1단계에서는 `ErrorResponse`, `TraceIdGenerator`, `SecurityConfig`를 구현하고 MVC·보안·서블릿 오류 처리와 요청 추적 필터를 추가했다. `AuthenticatedMember`와 JWT 발급·검증 설정은 3-1단계에서 구현했다. `WebSocketConfig`, `GrpcClientConfig`는 빈 골격이다. 자세한 현재 공통 동작은 [shared](SHARED.md)를 참고한다.

전체 테스트 97개는 기존 기반·DB·회원·실내 조회 검증에 모델 키·버전·코드 구분, 연결 누락·비활성·입력 오류와 매핑 조회 SQL 횟수 검증을 더한다. 소셜 인증·실제 앱·모델 연동은 포함하지 않는다.
