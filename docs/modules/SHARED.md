# shared — 최소 공통 지원 영역

작성일: 2026-09-10 · 갱신일: 2026-09-18 · 상태: 공통 오류·HTTP 추적 구현, 나머지는 설계

[전체 모듈 안내](README.md) · [Spring 구현 계획](../../IMPLEMENTATION_PLAN.md) · [DB 스키마](../../DATABASE_SCHEMA.md)

## 1. 무엇을 하는 영역인가?

shared는 여러 모듈이 함께 쓰는 작은 표현과 도구를 모아 두는 곳이다.

예를 들어 회원가입 오류와 장소 조회 오류가 앱에서 전혀 다른 형식으로 도착하면 앱은 기능마다 오류 처리 코드를 따로 만들어야 한다. 공통 오류 형식을 정하면 앱은 같은 방법으로 오류 코드와 안내 문구를 읽을 수 있다.

다만 shared는 회원·장소·즐겨찾기처럼 업무를 수행하는 독립 모듈이 아니다. 업무 모듈을 돕는 지원 영역이다.

## 2. 무엇을 넣고 무엇을 넣지 않는가?

| 둘 수 있는 것 | 넣지 않을 것 |
|---|---|
| 공통 오류 응답의 형태 | 회원가입·로그인 업무 흐름 |
| 최소 인증 주체 정보 | JWT 발급·일반 비밀번호·소셜 인증/연결 로직 |
| 정말 공통인 페이지 응답 표현 | 장소·즐겨찾기 JPA 엔티티 |
| 공용 시각 제공·추적 ID 도구 | 모델 추론·센서 전처리·네이버 검색 어댑터 |
| 공통 로그 마스킹 규칙 | 모든 모듈의 Repository를 모은 서비스 |

처음부터 표의 모든 도구를 만들 필요는 없다. 실제로 필요한 공통 부분부터 추가한다.

“여러 곳에서 쓸 수도 있다”는 이유만으로 모든 코드를 shared에 넣으면 역할을 찾기 어려워진다. 특히 이름이 `CommonService`나 `Utils`라는 이유만으로 서로 다른 업무를 한 클래스에 모으지 않는다.

## 3. 다른 모듈과 어떻게 연결되는가?

```text
member ───────┐
place ────────┤
favorite ─────┼──→ shared
positioning ──┘

shared → 업무 모듈 내부 코드: 참조하지 않음
```

화살표는 Java 코드가 다른 영역의 기능이나 타입을 사용한다는 뜻이다. 네트워크 요청이 아니다.

예를 들어 member와 favorite가 같은 오류 DTO를 사용하는 것은 가능하다. 반대로 shared의 오류 처리기가 favorite Repository를 호출해 즐겨찾기를 삭제하면 책임을 벗어난다.

모듈들을 실제로 연결하는 설정은 애플리케이션의 조립 지점에서 작성한다. 예를 들어 루트 `config/`에서 member가 제공하는 인증 설정을 Spring Security에 연결한다. 이 설정을 억지로 shared에 넣어 양방향 참조를 만들지 않는다.

## 4. 오류 응답은 어떻게 통일하는가?

예시: 이미 등록한 장소를 즐겨찾기에 다시 추가한다.

1. favorite가 중복이라는 업무 상황을 판단한다.
2. favorite가 그 의미를 나타내는 오류를 발생시킨다.
3. REST 오류 변환 계층이 HTTP 상태와 공통 응답 형태로 바꾼다.
4. 앱은 오류 코드로 상황을 구분하고 메시지를 보여 준다.

```text
favorite의 중복 판단
  → FAVORITE_DUPLICATE 오류
  → 공통 REST 오류 응답
  → 앱의 일관된 오류 표시
```

현재 공통 응답은 `code`, `message`, `traceId`, `errors`를 사용한다. 아래 즐겨찾기 업무 코드는 후속 구현 예시이며 아직 등록한 코드가 아니다.

```json
{
  "code": "FAVORITE_DUPLICATE",
  "message": "이미 등록한 즐겨찾기입니다.",
  "traceId": "example-request-123",
  "errors": []
}
```

| 항목 | 의미 |
|---|---|
| code | 앱이 오류 종류를 구분하는 안정적인 값 |
| message | 사람이 이해할 안내 문구 |
| traceId | 운영자가 해당 요청의 문제를 찾기 위한 식별자 |
| errors | 검증 실패 필드와 안내 목록, 없으면 빈 배열 |

traceId에 회원 ID나 위치를 그대로 넣지 않는다. 오류 메시지에 SQL·스택 트레이스·토큰도 포함하지 않는다.

모든 업무 오류의 규칙을 shared에 모을 필요는 없다. 오류의 의미는 소유 모듈이 관리하고, 공통 계층은 그 의미를 정해진 응답 모양으로 변환한다. 새 모듈이 생길 때마다 shared가 그 내부 클래스를 직접 참조하지 않도록 공통 계약이나 모듈별 어댑터를 사용한다.

### 4.1 인증 오류도 Controller 오류 처리기로 해결되는가?

전부 그렇지는 않다. Spring Security는 Controller에 도착하기 전에 요청을 거절할 수 있다.

현재 `GlobalExceptionHandler`가 MVC 오류를, `SecurityErrorResponseWriter`가 보안 필터 오류를 같은 규격으로 변환한다. `SecurityConfig`에서 `AuthenticationEntryPoint`와 `AccessDeniedHandler`를 연결했다. 컨테이너의 내부 `/error` 처리는 `ApiErrorController`가 담당한다.

MVC의 400·404·405·415 같은 상태와 필요한 헤더를 유지하고 예외 상세는 공개하지 않는다. Bean Validation 실패는 필드명과 안전한 안내만 반환한다. 상태 확인 GET 두 개, 일반 가입·로그인 POST, 건물·층·활성 장소 조회 GET 7개를 공개하고, 내 정보 조회·이름 변경은 JWT로 보호한다. 나머지 경로는 기본 거절한다. JWT는 HS256 서명·issuer·audience·exp·iat·nbf·양수 회원 번호를 확인한다.

### 4.2 WebSocket 오류도 HTTP 응답으로 보내는가?

연결이 열린 뒤에는 일반 REST 응답 대신 약속한 WebSocket 이벤트로 알린다.

```text
REST 요청 오류      → HTTP 상태 + 오류 JSON
WebSocket 메시지 오류 → 오류 이벤트 + 필요 시 연결 종료
```

통신 방식에 맞는 표현은 달라도 같은 오류 코드의 의미는 일관되게 유지한다. 연결을 유지할지 종료할지는 positioning이 결정한다. shared가 모든 오류를 보고 임의로 측정 연결을 끊지 않는다.

## 5. 인증과 권한은 어느 영역의 책임인가?

인증은 사용자가 누구인지 확인하는 것이고, 권한 검사는 그 사용자가 해당 일을 해도 되는지 확인하는 것이다.

| 책임 | 담당 |
|---|---|
| 일반 인증·소셜 연결·회원 상태·토큰 발급 정책 | member |
| 요청 토큰을 검증하고 사용자 정보를 전달하도록 연결 | 애플리케이션 보안 설정 |
| 인증된 회원 ID·권한·필요한 만료 정보의 공용 표현 | 필요한 경우 shared |
| 본인의 즐겨찾기만 삭제할 수 있는지 판단 | favorite |
| 장소를 수정할 권한이 있는지 판단 | place |
| 인증된 측정 연결 시작·만료·종료 | positioning |

현재 `AuthenticatedMember`는 JWT 검증을 통과한 내부 회원 번호를 전달하는 record다. 이 객체에는 필요한 식별 정보만 있고 비밀번호 해시나 JWT 서명 키는 없다.

일반·카카오·구글 로그인 이후 전달하는 공통 식별자는 MagNavi member_id다. 카카오 회원번호나 구글 sub를 그대로 공통 회원 번호로 사용하지 않는다.

shared의 인증 정보 객체 자체가 토큰을 검증하는 것은 아니다. 외부 입력을 그대로 넣어 인증이 끝난 것처럼 사용해서는 안 된다. 검증된 인증 결과에서만 생성·전달되도록 연결한다.

## 6. 입력 검증은 어디에서 하는가?

모든 검증을 shared에 몰아넣지 않고 목적에 맞게 나눈다.

| 검증 | 담당 위치 |
|---|---|
| 요청 필수값·문자 길이·숫자 형식 | 해당 모듈의 요청 DTO·입구 |
| 일반 로그인 ID 중복·소셜 계정 연결 충돌 | member와 DB 고유 제약 |
| 즐겨찾기 소유권·중복 대상 | favorite와 DB 제약 |
| 장소 좌표 범위·참조 정책 | place |
| 센서 순번·연결 상태·전송 한도 | positioning |
| 여러 모듈에 정말 동일하게 쓰이는 검사 도구 | 필요할 때만 shared |

예를 들어 센서 단위와 샘플 순서 규칙은 positioning의 책임이다. 숫자를 다룬다는 공통점만으로 shared가 모든 센서 규칙을 알아야 하는 것은 아니다.

## 7. 로그와 운영 정보는 어떻게 다루는가?

공통 로그 규칙은 “문제를 찾되 불필요한 개인정보는 남기지 않는다”다.

- 비밀번호·JWT·소셜 토큰/인가 코드·API Secret·서명 키·연락처는 기본 로그에 포함하지 않는다.
- 원문 검색어·네이버 응답 전체를 무조건 로그·캐시에 남기지 않는다.
- 센서 원본과 상세 예측 결과도 일반 로그에 남기지 않는다.
- 요청 실패 유형, 처리 시간, 연결 수, 대기열 길이는 집계 지표로 관찰한다.
- 회원 ID나 세션 ID를 지표의 분류 값으로 넣어 종류가 계속 늘어나게 하지 않는다.
- 추적 식별자는 필요한 기간과 접근 권한을 정해 관리한다.

공통 마스킹 규칙이 있어도 각 모듈에서 센서 DTO나 토큰 객체 전체를 출력하면 노출될 수 있다. 로그를 남기는 각 지점도 함께 검토해야 한다.

현재 `RequestTraceFilter`는 보안 필터보다 먼저 서버 UUID를 만들고 `X-Request-ID` 헤더·오류 JSON·로그에 연결한다. 요청에서 들어온 추적 헤더는 사용하지 않는다. 요청 로그에는 상태와 처리 시간만 남기고 요청이 끝나면 MDC(현재 스레드의 로그 부가 정보)를 정리하거나 이전 값으로 복원한다. 성공·실패·동시 실행의 정보 분리를 테스트했으며, 비동기 WebSocket·gRPC로의 추적 전달은 후속 구현 범위다.

DB 비밀번호와 JWT 키는 소스나 문서에 실제 값으로 적지 않는다. 환경 설정으로 주입하고, 필요한 값이 없으면 안전하게 실패하도록 설계한다. 환경 설정의 조립과 Actuator 공개 범위는 애플리케이션 운영 설정에서 관리한다.

## 8. 시간과 공통 도구는 왜 필요한가?

토큰 만료나 무응답 종료를 테스트하려고 실제로 몇 분씩 기다릴 필요는 없다. “지금 시각을 알려 주는 도구”를 바꿔 끼울 수 있으면 테스트에서 시간을 앞으로 옮길 수 있다.

Java의 `Clock` 같은 시각 제공 도구를 활용할 수 있다. 도구는 공용일 수 있지만 “몇 분 후 만료하는가?”라는 업무 정책은 member나 positioning이 소유한다.

2단계에서는 모든 업무 행의 같은 의미인 생성·수정 시각만 `AuditedEntity`로 공통화했다. Java `Instant`를 UTC·마이크로초 정밀도로 저장하고, 생성 시각은 갱신하지 않는다. `GeneratedIdEntity`는 자동 증가 ID를 쓰는 7개 엔티티가 공유하고 일반 인증은 회원 ID를 직접 사용한다. `DomainValues`는 존재·문자 수·양수 ID 같은 최소 검사를 제공하며 로그인·즐겨찾기 정책은 각 도메인에 둔다.

같은 이유로 페이지 응답이나 추적 ID 도구도 공통으로 사용할 수 있다. 다만 실제 기능에서 같은 의미로 사용되는 것이 확인된 뒤 공통화한다.

## 9. 초기 폴더 구성 예시

```text
shared/
├── error/          # 공통 오류 계약·응답 표현
├── security/       # 최소 인증 정보 표현, 필요한 경우
├── observability/  # 요청 추적
├── persistence/    # 생성·수정 시각·자동 증가 ID 매핑
└── validation/     # 공통 값의 존재·길이·양수 검사

config/             # 루트의 조립 지점; shared 내부가 아님
└── ...             # 보안·WebSocket·외부 설정 연결
```

현재 `error`에는 ErrorResponse·GlobalExceptionHandler·SecurityErrorResponseWriter·ApiErrorController, `observability`에는 TraceIdGenerator·RequestTraceFilter를 구현했다. 루트 config의 SecurityConfig도 동작한다. 2단계에서 persistence·validation의 최소 공통 지원을 추가했다. 3-1단계에서 AuthenticatedMember와 MemberTokenValidator를 구현했다. JWT 키·도구 조립은 config/JwtConfig가 맡는다. WebSocket·gRPC 설정은 빈 골격이며 추가 공통 도구는 실제 필요에 따라 구현한다.

회원·장소 엔티티를 같은 베이스 엔티티에 억지로 맞추는 것도 필수 사항이 아니다. 생성·수정 시각처럼 정말 같은 의미의 공통 항목인지부터 판단한다.

## 10. 트랜잭션과 데이터 소유권

shared는 별도의 업무 테이블을 소유하지 않는다. 일반 인증·소셜 연결은 member가, 장소 기준 정보와 검색 연동은 place가, 허용된 즐겨찾기 스냅샷은 favorite가 관리한다.

가입 시 회원과 로그인 수단을 함께 저장할 트랜잭션은 member가, 즐겨찾기 등록의 트랜잭션은 favorite가 정한다. 외부 인증·네이버 검색 통신을 긴 DB 트랜잭션으로 감싸지 않는다. shared에 “모든 요청을 하나의 트랜잭션으로 실행하는 서비스”를 만들지 않는다.

공통 오류 응답으로 바꿨다고 이미 보낸 네트워크 메시지까지 취소되는 것은 아니다. DB 작업 실패 시의 롤백과 외부 통신 실패 시의 종료·재시도는 별개의 처리다.

## 11. 완료 확인

- [ ] shared가 업무 모듈의 내부 코드·Repository에 의존하지 않는다.
- [x] 일반 REST 오류와 보안 계층 오류가 같은 응답 형식을 사용한다.
- [ ] WebSocket 오류는 positioning의 계약으로 전달된다.
- [ ] 오류·로그에 비밀정보나 센서 원본·위치 이력이 남지 않는다.
- [ ] 업무별 검증·권한·트랜잭션 규칙이 소유 모듈에 남아 있다.
- [ ] 필요한 경우 시각을 제어해 만료·무응답 테스트를 실행할 수 있다.
- [ ] 새 기능마다 공통 도구를 늘리지 않고 실제 중복과 의미를 확인한다.
